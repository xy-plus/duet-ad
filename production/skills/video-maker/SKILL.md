# video-maker

开关为真时不描述字幕或标志。

## 逐段分析

项目统一为 `segments[N>=1]`。每次只处理当前 segment 的 `work/keyframes/01.png` 至 `09.png`、联系表和 `manifest.json`；像素证据优先于辅助信息。九帧由后端按源时间冻结，模型无权选帧或修改其数量、顺序和字节。若 payload 另带 `user_reference_images[{reference_id,image_reference,sha256}]` 和 `user_replacement_instruction`，它们只属于后续目标替换，不能作为源视频像素证据，不能据此新增、合并、拆分或补写人物、实体、场景、occurrences 或 relations；本节点不解释或重排这些编号。

1. 按 01 至 09 顺序查看全部冻结帧；提取主体、场景、对象、动作、结果、镜头、构图、转场、空间关系和因果。
2. 只据已查看帧生成视觉提示词：使用用户语言，描述可见主体与对象、镜头与构图、按图片顺序的动作因果、相对节奏和 segment 时间轴；`visual_prompt` 必须显式描述本段的空间布局与运动方向：每个可见主体或关键物体在画面中的左、右、中、上、下位置，谁持有什么，动作的方向（如手从画面左侧伸入，向右下方倾倒），以及这些位置关系是否随时间变化；与源片段时长一致但不写具体秒数，不引入优化后内容、声音或不可见事实。关键镜头变化与产品镜头除事实描述外，追加一句功能归因——这个镜头设计为观众做了什么：归因句以"作用："前缀开头、显式标记为解释，措辞从功能词表中选用：建立人物 / 对比主张 / 积累证据 / 放大反应 / 让过程可懂 / 交接注意力；节奏写成"事实→感受"双句，先一句像素事实、再一句"作用："归因（功能词表与双句结构范式：hypit reference-video 指南，中文化自译）。多小节结构的段必须另起一句独立的整体节奏"事实→感受"双句，不允许只把节奏分散在小节标题里（2026-09-28 复验实测：九小节段缺少该句时节奏归因退化）。功能归因只写进逐段 visual_prompt，不进入项目级索引的 relations（项目级"不因常识补造功能"条款不变）。
3. `visual_prompt` 末尾还必须带以下必备段落；事实与归因分离：事实句照原纪律，只写像素可证实的事实、禁止猜测——本节点只记录，原视频无法提供的信息在全链路（含下游 fusion）一律禁止猜测或编造；归因必须锚定到已陈述的事实，以"作用："前缀显式标记，不得脱离事实独立评价：
   - 产品呈现（段标题逐字写“产品呈现”）：按“叙事角色 × 展示手法”双维记录本段产品如何被介绍。叙事角色——本段产品承担的角色：被演示的证据 / 被声称的对象 / 展示的材质 / CTA 落点；同一产品在一段中可承担多个角色，逐一写明（角色维度：hypit transformations 指南的产品多重角色思想，中文化）。展示手法（手持展示、质地特写、使用演示、前后对比、镜头强调）、演示的身体部位与接触方式、镜头如何配合（推近、特写、环绕）照原纪律逐项记录。本段无产品呈现时逐字写“本段无产品呈现”，不得编造。手法词表出自 Seedance 社区工作流五分类 [FIELD: seedance.tv 工作流博客]，非官方文档。

逐段最终回答以本次注入的 JSON Schema 为唯一格式权威。模型只填写视觉提示词文本；segment、帧序、九帧字节、校验和、业务文件与正式发布均由后端负责。禁止创建或修改 `prompt.txt`、`keyframes/` 或其他业务输出。

## 项目级索引

仅当 `work/project_index_request.json` 声明 `phase="project_index"` 时执行一次。输入是所有 segment 的半尺寸分析副本及 SHA，以及各段已完成的 `visual_prompt` 防漏清单；按 segment、frame 顺序查看全部帧，不读取 `prompt.txt`，只输出元素索引。用户参考图和替换说明即使随 payload 同时传入，也只证明期望的目标外观，绝不能被当作源视频中已有对象或跨帧同一性的证据。

先逐帧列出直接可见的人物、可独立移动或被动作作用的持久实体、场景以及元素间关系，再跨帧回查并合并。用调用内唯一的中性 `key` 互相引用，不要编码源属性；后端会机械分配稳定 ID。同一实例逐字复用；证据不足、特征冲突或同类实例可分别移动/接触时分开。硬切后重新依据当前帧确认；位置、相邻帧、服装颜色或叙事角色不能单独证明同一性。碎片、倒影、残影、模糊、过渡扫到的背景杂物不升格；occurrence 只记录当前帧可证实内容。

合并前先在内部建立逐段覆盖账本。`segments[].visual_prompt` 只作为防漏清单，不是新的视觉事实：对其中提到的每个人物、手/手臂、手持物、可操作物和场景逐项回看对应九帧；像素能证实时必须进入索引，像素不能证实时忽略。完成跨段合并后，再按每个 segment 回查一次账本，确保每个已证实实例都有 key，且它在后来片段再次出现时把 occurrence 追加到同一个 key。所有 occurrence 的 `segment_index` 必须逐字复用对应输入段的值，不得改成从 0 开始或重新编号。两个物体若同帧出现、能分别持有/移动/接触，必须保持不同 key，不得因颜色、用途或外形相近而合并；后续更清晰的帧应纠正早先的局部误判，例如不能把清晰可见的瓶子继续写成胶囊。该覆盖核对只影响本次模型输出，不新增字段。

输出格式以本次调用注入的 JSON Schema 为唯一权威。`people/entities/scenes/relations` 都是数组，调用内引用写入各记录的 `key`；人物、实体和场景记录包含 `source_visual_description/occurrences/replaceable/preserve`，关系记录包含 `subject_key/predicate/object_key/occurrences/preserve/replace_together`，关系逐帧记录包含 `frame_order/state/geometry`。后端把调用内 `key` 机械映射为稳定 ID；不接受重复 key、额外字段或缺字段。

`scenes` 必须非空，且每个输入帧必须且只能归属一个 scene occurrence；所有 scene occurrences 合并后逐项等于输入中的全部 segment/frame，不得引用未知帧、重复归属或漏帧。人物、实体和关系只记录有直接证据的内容，可以为空。

关系必须是像素可证实的物理、空间或功能关系，例如连接、容纳、持有、驱动、释放、接触、支撑或组成；用 `subject_key/predicate/object_key` 固定角色，不能把主客体互换。逐帧记录当前状态和相对几何，使装配、作用、释放、分离等变化保持同一关系 ID；这是下游逐帧关系状态和几何的唯一 producer，后续 phase 不重新生成。仅当两个元素需要保持同一可见交互事件及其时序时设 `replace_together=true`；它不得使用户图绑定的替换物继承源物品的接口、形状、体积、尺度、比例或功能，接触几何由下游按新物品自然重建。不因常识补造功能，不把动作先后误写为关系。

`replaceable` 只写可替换属性，`preserve` 只写必须保持的身份、交互事件或连续性。对可能绑定用户图的实体，`preserve` 不得把源物品的形状、体积、尺度、比例或功能写成后续替换约束；这些特征只由参考图决定。空类别写 `[]`。只填写 Schema 字段；后端校验冻结输入并原子发布。
